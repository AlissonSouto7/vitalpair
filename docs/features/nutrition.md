# Feature: nutrition

- **Status**: shipped
- **Owner**: @AlissonSouto7
- **Last updated**: 2026-09-28

## What it is and where it lives

Logging what a person eats and telling them where they stand against their
targets for the day. Food comes from three places: a search against Open Food
Facts, a barcode lookup against the same API, or typed in by hand. A fourth path,
a photo analysed by AI, lives in the `mealvision` package and finishes here, by
posting a log like any other.

This is the reference feature for the architecture. When a layering question
comes up, the answer is whatever `nutrition` does.

|                   |                                                         |
| ----------------- | ------------------------------------------------------- |
| Frontend route    | `/nutrition`                                            |
| Who can access it | authenticated user; every endpoint requires a token     |
| Backend package   | `com.aps.vitalpair.nutrition` (57 classes, 2,432 lines) |
| Feature flag      | none                                                    |

### Endpoints

All under `/api/v1/nutrition`, all requiring a valid access token.

| Method | Path                    | Action                                           |
| ------ | ----------------------- | ------------------------------------------------ |
| GET    | `/foods/search?q=`      | Search Open Food Facts by name                   |
| GET    | `/foods/barcode/{code}` | Look up one product by barcode; 404 when unknown |
| POST   | `/logs`                 | Log a meal. Publishes `MealLoggedEvent`          |
| GET    | `/logs?date=`           | The day's logs for the caller, oldest first      |
| DELETE | `/logs/{id}`            | Delete one of the caller's own logs              |
| GET    | `/summary?date=`        | Totals for the day against the caller's targets  |
| GET    | `/favorites`            | The caller's eight most repeated foods           |

The cart, under the same prefix. Every one acts on the caller's own cart: the
owner comes from the token, and there is deliberately no `/carts/{userId}`.

| Method | Path                   | Action                                                          |
| ------ | ---------------------- | --------------------------------------------------------------- |
| GET    | `/cart?date=`          | What is staged for a day, oldest first. No date means today     |
| POST   | `/cart/items`          | Stage one food. Writes nothing to the diary                     |
| DELETE | `/cart/items/{id}`     | Remove one staged item. Somebody else's answers 404             |
| DELETE | `/cart?date=`          | Empty the day's cart without logging it                         |
| POST   | `/cart/checkout?date=` | Log every staged item and empty the cart. All or nothing (R-16) |

The photo endpoint, `POST /api/v1/nutrition/photo`, is served by
`mealvision`'s `NutritionPhotoController` under the same URL prefix. It analyses
an image and returns candidate foods; it does not write a log. See
[meal-vision.md](meal-vision.md).

### Data

| Table                  | Created in                           | Notes                                                                                                                         |
| ---------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `food_logs`            | `V2__create_food_logs.sql`           | `tenant_id` and `user_id` both `NOT NULL` with FKs. Indexes on `(tenant_id)` and `(user_id, logged_at)`                       |
| `food_logs.is_private` | `V7__feed_reactions_and_privacy.sql` | Default `FALSE`. A private log still scores points but is not shown to the partner                                            |
| `meal_cart_items`      | `V31__create_meal_cart.sql`          | Same columns as `food_logs`, plus `consumed_on DATE` and `expires_at`. Indexed on `(user_id, consumed_on)` and `(expires_at)` |

Database constraints, not just application rules: `meal_type IN ('BREAKFAST',
'LUNCH', 'DINNER', 'SNACK')` and `source IN ('OPEN_FOOD_FACTS', 'MANUAL')`.

## Business rules

| #    | Rule                                                                                                                                           | Why                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R-1  | `tenant_id` is copied from the user at write time, never taken from the request                                                                | A tenant id a client can send is a tenant id a client can change                                                                                                                                                                                                                                                                                                                                                                           |
| R-2  | Null macros are stored as zero, not null                                                                                                       | The summary sums them. A null in one row would otherwise have to be handled at every read                                                                                                                                                                                                                                                                                                                                                  |
| R-3  | `loggedAt` defaults to now when the client does not send one                                                                                   | Backdating is allowed on purpose: people log lunch in the evening                                                                                                                                                                                                                                                                                                                                                                          |
| R-4  | Deleting a log belonging to someone else returns 404, not 403                                                                                  | 403 confirms the id exists, which turns the endpoint into a probe for other people's records                                                                                                                                                                                                                                                                                                                                               |
| R-5  | A day runs midnight to midnight in UTC (`ZoneOffset.UTC` in `FoodLogPersistenceAdapter`)                                                       | Consistent boundaries across the whole codebase. This is wrong for a user in `America/Sao_Paulo` after 21:00 local, recorded as N-3 below                                                                                                                                                                                                                                                                                                  |
| R-6  | The summary returns `remaining = null` when the user has no calorie target                                                                     | Showing "remaining: 2000" to someone who never set a target is a number invented by the server                                                                                                                                                                                                                                                                                                                                             |
| R-7  | Favourites are the eight most frequently logged food names, with the most recent entry supplying the quantity and macros                       | Re-logging the same breakfast is the most common action in the app                                                                                                                                                                                                                                                                                                                                                                         |
| R-8  | A search failure returns an empty list, not an error                                                                                           | Open Food Facts being down should degrade the search box, not break the meal screen                                                                                                                                                                                                                                                                                                                                                        |
| R-9  | Open Food Facts is called with 3s connect and 5s read timeouts, retried at most twice and only on `ConnectException`, behind a circuit breaker | Detailed in [observability.md](observability.md). A read timeout means the server answered and went quiet; retrying that only multiplies the wait                                                                                                                                                                                                                                                                                          |
| R-10 | Logging a meal publishes `MealLoggedEvent` `AFTER_COMMIT` with `REQUIRES_NEW` listeners                                                        | Gamification, the feed and notifications all react. A listener failing must not roll back the meal the person just logged                                                                                                                                                                                                                                                                                                                  |
| R-11 | An imported meal whose calories **and** every macro are zero is refused with 422                                                               | That is the shape "no nutrition data" takes, not the shape a food takes. Deliberately narrow: a hand-entered 0 kcal meal still saves, because black coffee and water really are zero, and a blanket "calories > 0" would make the diary wrong in the other direction                                                                                                                                                                       |
| R-12 | Deleting a meal publishes `MealDeletedEvent`                                                                                                   | The feed keeps its own copy, so removing the diary row is half the deletion. See [feed.md](feed.md) R-9                                                                                                                                                                                                                                                                                                                                    |
| R-13 | The cart belongs to one person, not to the pair, and no endpoint reads or writes somebody else's, not even the partner's                       | Everything else here is shared on purpose. The cart is the plate somebody is still building; a partner reading it, or confirming it, is not a feature anybody asked for                                                                                                                                                                                                                                                                    |
| R-14 | A cart item's day defaults to the caller's own day, never the server's                                                                         | The server runs UTC. At 22:00 in Brazil it is already tomorrow there, and dinner would be staged against the wrong date                                                                                                                                                                                                                                                                                                                    |
| R-15 | At most 50 items per person per day                                                                                                            | Not about eating a lot: the endpoint writes one row per call, so without a cap one account can fill the table by itself. Fifty is past any real plate                                                                                                                                                                                                                                                                                      |
| R-16 | Checkout is all or nothing, inside one transaction                                                                                             | Half a lunch recorded is worse than none, because the person cannot tell what is missing without checking item by item. On failure the cart is left intact so they can retry                                                                                                                                                                                                                                                               |
| R-17 | Checkout goes through `LogMealUseCase`, never straight to the repository                                                                       | Logging a meal is not just a row: it publishes the event that scores, feeds the pair's wall and notifies. A cart that wrote rows itself would be a path that silently does not score                                                                                                                                                                                                                                                       |
| R-18 | Every cart item carries `expires_at`, and an hourly sweep deletes what has passed it                                                           | An abandoned cart is dated rubbish. Two days covers staging dinner and confirming the next morning, and still keeps the table clean                                                                                                                                                                                                                                                                                                        |
| R-19 | Null macros are stored as zero on the cart too, exactly as R-2 does on the diary                                                               | The request marks them optional because the search returns foods whose macros nobody knows. The columns are `NOT NULL`, so the absence has to become a zero or an ordinary entry is a 500                                                                                                                                                                                                                                                  |
| R-20 | Checkout reads the day's items with a row lock (`findForCheckout`, `PESSIMISTIC_WRITE`); every other read does not                             | Reading, writing and clearing are separate steps in one transaction, so two taps on the button would both read the same list and log the same lunch twice, with the points counted twice. The loser waits, finds the cart empty and stops on R-16's empty-cart rule. A screen read must not pay that cost or hold anybody's rows                                                                                                           |
| R-21 | Every catalogue food carries a family, read from the `# categoria:` directive that opens its section in the CSV and valid until the next one   | The screen shows an icon and a word per line so a list of similar names can be skimmed before it is read. In the file rather than a column because the sections already existed: a column would repeat the same word a hundred times and let one line disagree with the heading it sits under                                                                                                                                              |
| R-22 | An unknown family in the catalogue file becomes `OTHER` with a warning, it does not fail startup                                               | Same reason a malformed line does not: a typo in a catalogue file must not take the application down. The cost is one section without an icon, visible on screen and in the log                                                                                                                                                                                                                                                            |
| R-23 | A branded product from Open Food Facts is always `OTHER`                                                                                       | Their categories describe packaged brand products and do not map onto these families. Translating theirs into ours from the product name would be inventing the information                                                                                                                                                                                                                                                                |
| R-24 | The portions offered come from the name first and the family second                                                                            | A family is coarser than a portion: `TREAT` covers a biscuit and a soft drink, and a glass is not a portion of biscuit. Where the name recognises the food it is more specific; where it does not, the family beats the generic 50/100/200g                                                                                                                                                                                                |
| R-25 | Each portion button shows the calories of that portion, and shows nothing when they are unknown                                                | Whoever is choosing the portion is deciding how much to eat, and it is the calories that answer that. "0 kcal" on a food with no nutrition data would assert the portion has none, which is not what "unknown" means                                                                                                                                                                                                                       |
| R-27 | The search returns at most 10 items, and a food with no nutrition numbers is pushed below every food that has them                             | Measured on an iPhone 12 on 2026-09-28: "arroz" returned 20, 3 from the catalogue and 17 branded products, and the list pushed the editor far below what the person was looking at. Choosing an item with no numbers costs filling them in by hand, so it ranks last; it stays in the list because somebody may want that exact brand                                                                                                      |
| R-28 | The search list shows the family and nothing else under the name; provenance moved into the editor                                             | Measured on an iPhone 12: family and provenance together truncated on all five visible results, so the provenance showed cut off and sometimes ate the end of the family. Two pieces of information in a line that fits one are not two pieces of information. The family answers "is this what I want?", which is the question while choosing; the provenance answers where the number came from, which is the question while checking it |
| R-26 | A meal can be logged for today, yesterday or the day before, and the instant sent keeps the current time of day                                | Somebody who forgets dinner and opens the app next morning had no way to say so, and the streak, the ledger and the competition are counted by date. Midnight would be wrong: 00:00 is the edge of the day, so anybody behind UTC would land on the day before the one they picked                                                                                                                                                         |

### What is not covered

- **The real Open Food Facts API.** Every test runs against WireMock replaying captured
  fixtures. A change to their response shape would not be caught here.
- **Concurrent logs.** Two requests logging a meal at the same instant are not tested.
  Nothing is decremented and no uniqueness is claimed, so the expected result is simply two
  rows, but that is reasoning, not a measurement.
- **The summary at a day boundary.** No test covers a meal logged at 23:59 UTC, which is
  where N-3 shows.
- **Favourites with a food logged under two spellings.** Grouping is by exact name, so
  "Banana" and "banana" are two entries. No test asserts either behaviour.
- **A very large day.** No test covers a user with hundreds of logs in one day; the summary
  loads them all into memory.
- **The frontend nutrition page.** Covered by no Playwright test. The browser suite exercises
  authentication, navigation and accessibility only.
- **The bottom bar has no test.** Its position, size and centring were measured in a browser
  on an iPhone 12 and recorded above, but nothing asserts them on every build: a change to the
  layout could move the "+" off centre and no test would fail.
- **The icons are not asserted.** Ten paths were drawn, rendered at 16, 32 and 64px and looked
  at; five were redrawn because they read as a pot, a battery, a pear, an outline and a generic
  cup. Nothing stops the eleventh from being unreadable.
- **The cart has no screen yet.** The backend is complete and tested; nothing in the app calls
  it. Until the frontend lands, the endpoints exist and no user can reach them.
- **Checkout rolling back against a real database.** All-or-nothing is proven in
  `MealCartServiceTest.umItemQueFalhaNaoDeixaMetadeDoAlmocoRegistrada`, where the failure is
  injected into a mock. No integration test forces an item to fail mid-transaction, because
  making a real one fail means corrupting a row on purpose. The rollback itself therefore rests
  on `@Transactional`, which is read rather than measured.
- **The 50-item cap under concurrency.** The count and the insert are not atomic, so parallel
  requests can overshoot it slightly. Deliberately left: the cap exists to stop one account
  filling the table, which a few extra rows do not defeat, and locking the day's rows on every
  add would slow down the common path to guard against nothing.

## How to verify in production

```sql

SELECT source, count(*) FROM food_logs
```

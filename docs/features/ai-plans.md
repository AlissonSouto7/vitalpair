# Feature: AI plans (meal and workout)

- **Status**: shipped
- **Owner**: @AlissonSouto7
- **Last updated**: 2026-09-06

## What it is and where it lives

A week of meals and a week of workouts, generated by Anthropic from the person's
own targets. The meal plan is seven days of four meals with macros per dish, and
any single meal can be swapped for an alternative. The workout plan is seven days
of four to five training sessions plus rest days, with the exercises tickable and
the day markable as done, which logs an activity.

This is the most expensive feature in the product: every generation is a paid call
that takes around twenty seconds. Most of the design decisions here follow from
that.

|                   |                                                                           |
| ----------------- | ------------------------------------------------------------------------- |
| Frontend routes   | `/meal-plan`, `/workout-plan`                                             |
| Who can access it | authenticated user; the plan is the caller's own                          |
| Backend package   | `com.aps.vitalpair.ai` (64 classes, 2,276 lines, the largest feature)     |
| Feature flag      | none, but the whole feature returns 503 when `ANTHROPIC_API_KEY` is blank |

### Endpoints

| Method | Path                                         | Action                                               | Rate limit       |
| ------ | -------------------------------------------- | ---------------------------------------------------- | ---------------- |
| GET    | `/api/v1/meal-plan`                          | This week's plan, or `data: null` with 200 when none | none             |
| POST   | `/api/v1/meal-plan/generate`                 | Generate the week, replacing any existing plan       | 5/hour per user  |
| POST   | `/api/v1/meal-plan/swap`                     | Replace one meal with an alternative                 | 20/hour per user |
| GET    | `/api/v1/workout-plan/today`                 | Today's session, or `data: null`                     | none             |
| POST   | `/api/v1/workout-plan/generate`              | Generate the week, return today                      | 5/hour per user  |
| POST   | `/api/v1/workout-plan/exercises/{id}/toggle` | Tick or untick one exercise                          | none             |
| POST   | `/api/v1/workout-plan/complete`              | Mark today done, log a `WORKOUT` activity            | none             |

The limits are per **user**, not per IP, because the concern is one account running
up a bill rather than one network location. The reads and the toggle are free
operations and are not limited.

### The call to Anthropic

|               | Meal week   | Meal swap   | Workout week   |
| ------------- | ----------- | ----------- | -------------- |
| `max_tokens`  | 8192        | 1024        | 8192           |
| Metric `kind` | `meal-plan` | `meal-swap` | `workout-plan` |

The client is a dedicated Feign interface, `AnthropicPlanClient`, separate from the
photo one purely because plans need a longer read timeout: 5s connect and **60s
read**, against 30s for a photo. The test profile shortens both so a timeout test
does not take a minute.

Every request sends `output_config.format = json_schema` with a closed schema
(`additionalProperties: false`, full `required` list). Without it the model answers
in prose and the parse fails. `temperature`, `top_p` and `thinking` are
deliberately not sent: the model in use rejects them with a 400.

The response is parsed defensively, because a schema is a request and not a
guarantee: days outside 0..6 are dropped, duplicate day/meal slots are deduplicated,
an unknown meal type is discarded, a workout day that ends up with no exercises is
downgraded to a rest day, and any missing day is filled with a rest day so the week
always has seven.

## Business rules

| #   | Rule                                                                                    | Why                                                                                                                                                                                                                                    |
| --- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-1 | A week starts on Monday, everywhere                                                     | The scoreboard, the plan and the season all bucket by week; one anchor avoids three ways of being off by a day                                                                                                                         |
| R-2 | Generating replaces the week instead of appending                                       | `UNIQUE (user_id, week_start)` makes it the only correct behaviour, and a person regenerating wants a new menu, not two                                                                                                                |
| R-3 | A profile without a calorie target is refused with 422 **before** any call is made      | The paid call would produce a plan built on a number the user never set. `AnthropicPlanGenerationIT.anIncompleteProfileIsRejectedBeforeSpendingMoney` asserts WireMock received nothing                                                |
| R-4 | Anthropic is never retried                                                              | A retry doubles the cost of a call that takes up to a minute, and repeats it exactly when the partner is struggling                                                                                                                    |
| R-5 | A model refusal or an unparseable answer does not count towards the circuit breaker     | Those mean the partner answered and the answer is unusable, which says nothing about its health. Counting them let a handful of unusual prompts disable the feature for everyone, which happened before `PlanContentException` existed |
| R-6 | Both plan tables carry `tenant_id`, and every root query filters by user **and** tenant | See A-1 below: they did not, and the migration that added the column shipped a 500                                                                                                                                                     |
| R-7 | Completing an already-completed day is a 409, and completing a rest day is a 422        | Two different mistakes deserve two different answers                                                                                                                                                                                   |
| R-8 | A failed generation persists nothing                                                    | Half a week of meals is worse than none. `anOverloadedApiBecomesA502NotA500` checks the subsequent GET returns `null`                                                                                                                  |
| R-9 | Every failure reaching the client is a 502 or 503, never a 500                          | A partner problem is not an application bug, and the message tells the person whether to retry now or later                                                                                                                            |

## Security findings

### Fixed

| ID  | Severity | File                                | What happened                                                                                                                                                      | Measured impact                                                                                     | Fix                                                                                                                                                                                                                                |
| --- | -------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-1 | High     | `V22` plus both adapters            | `V22` added `tenant_id NOT NULL` to both plan tables, and no adapter ever wrote it. Every plan generation failed with a constraint violation, returned as HTTP 500 | The whole feature, from the day V22 was applied. Reproduced against the running demo before the fix | `tenantId` threaded through the domain records, the ports, the entities and the adapters. `AnthropicPlanGenerationIT.aGeneratedPlanIsStoredWithItsTenant` reads the column back with raw JDBC and compares it to the user's tenant |
| A-2 | High     | plans scoped by `user_id` alone     | Before V22 the only thing between one pair's plans and another's was every query remembering to filter correctly                                                   | Not exploited: `TenantIsolationIT` was written at the same time and found no live leak              | The tenant column plus a filter on both ids in every root query                                                                                                                                                                    |
| A-3 | Medium   | `application.yaml` resilience block | A model refusal counted as a partner failure, so five refusals opened the breaker and disabled generation for every user for 60 seconds                            | Predicted and then confirmed                                                                        | `ignore-exceptions` listing the content exceptions. `CircuitBreakerIT.aModelRefusalDoesNotOpenTheBreaker` proves five refusals leave the breaker `CLOSED`                                                                          |
| A-4 | Medium   | no limit                            | Generation had no rate limit while calling a paid API                                                                                                              | One account could issue unbounded paid calls                                                        | 5/hour per user for generation, 20/hour for a swap                                                                                                                                                                                 |

### Open

| ID   | Severity      | File                                    | What happens                                                                                                                                                                                                | Measured impact                                                                                                                                                                 | Why it is still open                                                                                                |
| ---- | ------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| A-5  | Medium        | `AnthropicMealPlanGenerator#swapPrompt` | The swap prompt interpolates the stored dish name into the next prompt inside unescaped double quotes. The name is model output, bounded only by `VARCHAR(255)`                                             | Not user-controlled: the person can only trigger a regeneration, not choose the string. So this is untrusted text flowing into a paid prompt, not an injection a caller can aim | Everything else interpolated is a number or a closed enum. Worth bounding and escaping; recorded rather than rushed |
| A-6  | Medium        | both `replace` adapters                 | Generation is read, delete, insert with no lock. Two concurrent generations for the same user and week can both pass the check, and the second insert can violate the unique constraint, surfacing as a 500 | The 5/hour limit narrows the window but does not close it. Not reproduced under test                                                                                            | Fixing it properly means an upsert or a lock; the honest interim is that it is recorded and rate limited            |
| A-7  | Medium        | `MealPlanService#swap`                  | If the item id does not match the plan, `updateItem` silently does nothing and the caller gets 200 with an unchanged plan, having been billed for the call                                                  | Reachable only by sending an id belonging to another plan, which the ownership filter already restricts to the caller's own                                                     | A silent no-op on a write path should be an explicit failure. Backlogged                                            |
| A-8  | Low           | `WorkoutPlanPersistenceAdapter`         | `findByExerciseId`, `setExerciseDone` and `setDayCompleted` are unscoped `findById` calls; ownership is enforced one layer up in the service                                                                | The service check is present and correct, verified by reading it and by `TenantIsolationIT`. So there is no live hole, only a defence that is one refactor from being lost      | The meal side has a scoped `findByIdAndPlanId` query to copy. Worth closing the asymmetry                           |
| A-9  | Low           | both generators                         | A single breaker named `anthropic` is shared with photo analysis, so five failing generations also stop photo analysis for 60 seconds                                                                       | Deliberate: it is one partner. But the two paths have different timeouts and token budgets, so they are not equally likely to fail                                              | Splitting them is a config change, worth doing if the failure modes ever diverge in practice                        |
| A-10 | Informational | `MealPlanService#generate`              | Takes a `tenantId` parameter and then uses `user.getTenantId()` instead. The same in `WorkoutPlanService`                                                                                                   | Not exploitable: both come from the same authenticated principal                                                                                                                | The parameter should be used or removed. Left as a note so the next reader does not assume it is honoured           |

### Verified and fine

| Check                                     | How it was verified                                                                                                                                                                                                | Date       |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------- |
| The API key never reaches a log           | Only `ex.getMessage()` is logged, and request URIs pass through `LogSafe.value(...)` in both exception handlers                                                                                                    | 2026-09-06 |
| No unbounded retry on a paid call         | There is no `resilience4j.retry.instances.anthropic` at all; the only retry instance is `openfoodfacts`, capped at 2 attempts for `ConnectException`                                                               | 2026-09-06 |
| Every paid endpoint has a per-user limit  | The four cost-bearing routes appear in `RateLimitFilter.POLICIES`; `RateLimitIT.planGenerationIsCappedPerUserNotPerAddress`                                                                                        | 2026-09-06 |
| A missing key fails before any HTTP call  | `AnthropicProperties.isConfigured()` short-circuits into a 503                                                                                                                                                     | 2026-09-06 |
| Plans are stored with the caller's tenant | `aGeneratedPlanIsStoredWithItsTenant`, using raw JDBC rather than the same mapper that writes it                                                                                                                   | 2026-09-06 |
| No cross-tenant plan read                 | `TenantIsolationIT` gives the second pair a fixture whose dish names are prefixed `BETA `, so a leak is detectable. Proved non-vacuous: with identical fixtures, sabotaging the tenant filter kept the build green | 2026-09-06 |

### What is not covered

- **Concurrent generation** for the same user and week, which is A-6.
- **The half-open state** of the circuit breaker. The tests cover closed and open only.
- **A partially valid model answer**: five days instead of seven, or a day with three
  meals. The parser handles it and no test exercises it.
- **The workout toggle and complete endpoints** have no dedicated test beyond the tenant
  isolation sweep.
- **Cost**. The `usage` block in the response is not deserialised at all, so token spend is
  neither recorded nor asserted anywhere.
- **The real Anthropic API.** Every test replays a fixture. A change in their response shape
  would not be caught here.

## How to verify in production

```sql
-- read only: plans generated per week
SELECT week_start, count(*) FROM meal_plans GROUP BY week_start ORDER BY 1 DESC LIMIT 8;

-- read only: a plan whose tenant does not match its user is A-1 regressing
SELECT count(*) FROM meal_plans p JOIN users u ON u.id = p.user_id WHERE p.tenant_id <> u.tenant_id;

-- read only: a week that is not seven days means the parser let something through
SELECT plan_id, count(DISTINCT day_index) AS days FROM meal_plan_items GROUP BY plan_id HAVING count(DISTINCT day_index) <> 7;
```

```bash
# read only: AI calls by kind and outcome, and the breaker state
curl -s localhost:9090/actuator/prometheus | grep 'vitalpair_ai_requests_total'
curl -s localhost:9090/actuator/prometheus | grep 'resilience4j_circuitbreaker_state.*anthropic'
```
